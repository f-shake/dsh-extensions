# 阶段一 · 深度计划

**目标**：把一句模糊的构想，逼成一份没有未决问题的开发计划。
**入口**：人给出初步构想。**出口**：人确认计划（闸门1）。

> 📌 本阶段**每一次回复**的末尾都要带阶段脚注（格式与措辞见 `SKILL.md` §0.1）。追问轮里通常是「继续本阶段 —— 等你回答上面 N 个问题」。

> 计划阶段宁可多花时间，也不要把不确定性带进代码阶段。

---

## 1. 采集初步设想（环节1）

人给出的原话是**输入**，不是素材。**不要补充、不要演绎、不要替他补全没说的部分**——没说的部分正是环节3 要问出来的。

记录三类信息：

| 类别 | 例子 |
|---|---|
| 想做什么 | 「给配置页加一个批量导入」 |
| 解决什么问题 | 「现在只能一条条手填，几十条要填半小时」 |
| 已知约束 | 「只支持 CSV，不要引入新的依赖」 |

若人不确定，**带着 2~3 个候选方向去问**，不要丢一句「请补充需求」。

---

## 2. 产出开发计划（环节2）

计划写进**项目里的计划文件**，不贴进聊天（回复只给路径 + ≤10 行摘要）。位置先找项目约定（`AGENTS.md` / `CLAUDE.md` / 现有 `docs/` 下的计划或设计文档）；找不到就带 2~3 个候选问人，不要默认。

计划文件本身是阶段一的产物：不计入计划里的修改范围，也不计入阶段二的计划外改动；是否提交由阶段五按用户意见处理。

计划必须**逐项**写明以下 11 项。每项后的「详尽判据」是及格线——达不到就是没写完。

| # | 目录 | 写到什么程度算详尽 |
|---|---|---|
| 1 | **功能需求** | 每条需求可被一条测试用例验证。含糊的形容词（「快」「好用」）必须量化或拆成具体行为 |
| 2 | **技术方案** | 说清选型与**为什么选它**，以及被否决的备选方案 |
| 3 | **系统结构** | 新增/改动了哪些层、哪些模块，画出模块间调用关系 |
| 4 | **数据结构** | 字段名、类型、可空性、默认值、约束；新表/新类型定义完整列出 |
| 5 | **模块划分** | 每个模块的职责边界——**它不负责什么**同样要写 |
| 6 | **交互逻辑** | 用户每一步操作后发生什么；状态如何流转 |
| 7 | **异常情况** | 每一类失败（网络、权限、数据非法、超时、并发）的**具体表现与提示文案** |
| 8 | **边界条件** | 空值 / 零 / 最大值 / 超长 / 重复 / 首次运行 / 无权限 |
| 9 | **修改范围** | 精确到文件列表，作为**基线**。清单要尽量列全，但不必假装它绝对完整 |
| 10 | **实现步骤** | 有序步骤，每步可独立验证 |
| 11 | **测试方案** | 覆盖哪些维度、测试文件落在哪、如何运行 |

> **文件清单是基线，不是铁律。** 它约束的是「别顺手改无关的地方」，不是「多改一个文件就是越权」——执行中必然会遇到清单没写、但不动就跑不通的文件（漏列的依赖、生成的 lock、漏列的测试文件）。这类差异按 `phase-2-implementation.md` §3 的偏差分级处置：**登记后继续**还是**停下回闸门1**，判据是「人拍板的『做什么』有没有变」，不是「文件在不在清单里」。

### 计划文档骨架

```markdown
## 1. 功能需求
## 2. 技术方案（含选型理由与否决方案）
## 3. 系统结构
## 4. 数据结构
## 5. 模块划分（职责 / 不负责什么）
## 6. 交互逻辑
## 7. 异常情况（含提示文案）
## 8. 边界条件
## 9. 修改范围（文件清单）
## 10. 实现步骤
## 11. 测试方案
## 附：未决问题（待环节3 追问）
```

---

## 3. 调用 `grilling` 追问澄清（环节3）

计划初稿写完**落盘后立即**调用，不要等人来指出问题。

```
调用（Skill 工具）：`grilling`
  兜底（Skill 工具不可用时）：读技能目录下的 `grilling/SKILL.md` 并照其执行
  调用时机：计划初稿已产出、尚存未决问题时
  传入：计划初稿 + 已知约束 + 你识别出的未决清单
  期望产出：按可问集分轮次的问题清单，每轮带推荐答案，**每轮必须等用户回答**
  返回后：把已确定的决策合并回计划，重算未决项，未清空则继续下一轮
```

**注意**：必须**分轮次**、**每轮等用户回答**，不要把问题一口气倒出来再自己往下推进。若本轮为查事实派了子代理，**等它们全部回报、重算可问集后再发问**，不要把一轮拆成「先问一半、回报后再问一半」；探查失败则按 `grilling` 的兜底规则**如实标成未查明**、转成待用户裁决的问题，不得因此卡住不发问。

### 追问要覆盖的方向

- **为什么**：「为什么要这样做？有没有更简单的做法能达到同样效果？」
- **是否需要**：「这个情况需要支持吗？还是可以先不做？」
- **异常怎么办**：「如果出现这种异常，用户看到什么？数据回滚吗？」
- **与现有模块的关系**：「这个功能和现有的 X 模块是什么关系？复用还是新建？」
- **另一种情况**：「这里是否存在另一种情况？（多用户/无权限/数据为空/重复提交）」

**grilling 的双重价值**：既让 AI 真正理解需求，也逼人自己把需求想清楚。很多问题是在追问中才暴露的——**暴露出来就是收益**，不要为了「显得顺利」而少问。

---

## 4. 人工审查计划（环节4）

追问结束后，把**计划文件**交给审查（不贴全文）。审查聚焦六问：

| # | 审查点 | 需要回答 |
|---|---|---|
| 1 | 需求是否理解正确 | 计划描述的是不是他真正想要的东西 |
| 2 | 技术方案是否合理 | 有没有更合适的做法；有没有过度设计 |
| 3 | 修改范围是否准确 | 该改的列全了；**不该改的没被牵连** |
| 4 | 是否遗漏关键场景 | 对照 §2 的 7/8 两项，逐个场景过 |
| 5 | 是否存在潜在风险 | 兼容性、性能、数据迁移、回滚 |
| 6 | 实现路径是否符合预期 | 步骤顺序合理，每步可验证 |

发现问题 → **回环节2 改计划、再回环节3 追问**，反复迭代到达标为止。

---

🛑 **闸门1：计划确认**

停在何处：计划已完整、追问已闭环。**此刻不得写任何一行代码。**

本轮输出（计划文件路径 + ≤10 行要点 + 逐条待确认项）：

```
计划文件：<路径>
计划要点：
  - 功能：<一句话>
  - 修改范围：<N 个文件，列关键几个>
  - 技术方案：<一句话>
  - 测试：<覆盖维度>
待确认项：
  1. <仍未定的事项，如果有>
  2. ...
```

向用户提问（照抄）：

> 开发计划已写入 `<路径>`，请打开文件审查。确认无误请回复「确认」，我将开始按计划一次性开发。
>
> 开发开始后我会开启**自动续行**（goal 模式）：由流程自己一轮接一轮推进到闸门2，不必你反复打「继续」。**不想用它就回「确认，但不用 goal 模式」**——那就回到一轮一停的老方式。（一种例外：若某个回合被输出上限硬截断，续行会失效，那时我会说明断点，你说一声「继续」即可。）
>
> ⚠️ **本平台没有 goal 工具时，照抄上面这段就是假承诺**——禁止使用。改抄：**「确认后我按计划一次性开发，每完成一项播报一次；做到闸门2 停下请你确认。**做一段停一次、由你打「继续」推进（本平台无自动续行）。**」**（判据见 `goal-continuation.md` 开头「前置」。）

未确认前禁止：
- 不得写任何代码
- 不得修改任何文件（**计划文件除外**——它是本阶段的产物）
- 不得「先搭个架子等你回」
- 不得进入阶段二
- 不得在确认到达之前 `create_goal`（建 goal 只允许发生在用户确认闸门1 的那一轮；**若那一轮含「不用 goal」之类的拒绝，则整轮都不许建**，见 `goal-continuation.md` §3）
- 模糊回复（「嗯」「哦」）视为**未确认**，必须再问一次

**出口分支**：收到「确认，但不用 goal 模式」——**照常进入阶段二**，只是不建 goal，并按 `goal-continuation.md` §5 转回一轮一停；进入阶段二后的脚注相应改为「继续本阶段 —— 已 x/N，做完这一段我停下等你示意」。

**平台没有 goal 工具（或不确定）→ 走同一条分支**：整份 `goal-continuation.md` 忽略，不建 goal、不承诺自动推进，脚注一律不写「无需你操作」。

**补充**：goal 只服务阶段二，到闸门2 就收口；阶段三一律一轮一停——这一点与本分支无关，任何平台都如此。
